# HappyLearn Phase 5 Operations, Backup, Monitoring, and Hardening Design

Date: 2026-07-28
Status: Approved for implementation planning

## 1. Purpose

Phase 5 adds a low-overhead operational control plane to the existing Go and
Vue modular monolith. The teacher receives one place to inspect application
health, storage, AI usage, security signals, alerts, backup history, and restore
verification. Operators receive automated encrypted backups, optional
S3-compatible replication, retention enforcement, structured metrics, and
repeatable recovery checks.

The phase must remain usable on the approved Ubuntu 24.04, 2 CPU, 4 GB target.
It must not weaken the role, ownership, secret handling, or audit guarantees
established in Phases 1 through 4.

## 2. Confirmed product decisions

- Local encrypted backup is mandatory and retains seven daily recovery points.
- Remote S3-compatible replication is optional. When configured, it retains
  thirty daily and twelve monthly recovery points.
- The default monitoring experience is the teacher-facing in-application
  dashboard and structured logs.
- A protected Prometheus endpoint is provided for optional external monitoring.
  Prometheus, Grafana, and exporters are not mandatory resident services.
- The teacher may change site presentation, retention, backup schedule, and
  alert thresholds.
- Database URLs, encryption keys, object-store credentials, webhook URLs, and
  other infrastructure secrets remain environment or owner-only secret-file
  configuration.
- Alerts appear in the teacher operations console and may also be delivered to
  an optional generic HTTPS webhook.
- Production releases use a single-host maintenance window. Phase 6 consumes
  the maintenance, backup, health, and release evidence introduced here.

## 3. Scope

### 3.1 Included

- Typed, versioned, non-secret system settings.
- Operational maintenance and drain state shared by the app, worker, and backup
  runner.
- Health and capacity sampling for the application, PostgreSQL, Redis, AIStor,
  AI execution, file processing, authentication, and host containers.
- Teacher dashboard, alert center, backup history, audit activity, and system
  settings UI.
- Encrypted PostgreSQL and AIStor backup recovery points with one batch ID.
- Optional remote S3-compatible replication.
- Backup retention and orphaned temporary-artifact cleanup.
- Disposable restore verification into an empty environment.
- Alert threshold evaluation, acknowledgement, automatic resolution, and
  bounded webhook delivery.
- Private Prometheus metrics.
- Structured log and secret-redaction hardening.
- Complete backend, frontend, integration, browser, security, recovery, and
  resource gates.

### 3.2 Excluded

- Destructive restore from the normal teacher web UI.
- Online editing of infrastructure credentials or webhook URLs.
- Public exposure of Prometheus metrics.
- A mandatory Prometheus, Grafana, Loki, or OpenTelemetry deployment.
- Multi-host failover, continuous PostgreSQL WAL archiving, and sub-24-hour RPO.
- Production server login, DNS changes, and certificate issuance. Those belong
  to the real-server portion of Phase 6.

## 4. Architecture

Phase 5 introduces two bounded Go domains:

- `internal/operations` owns settings, operational mode, dashboard aggregation,
  samples, alert state, webhook delivery, and Prometheus projection.
- `internal/backup` owns backup requests, runs, recovery-point metadata,
  retention, integrity checks, and restore-verification results.

The domains communicate through explicit interfaces. `operations` may read
backup summaries through a narrow query interface but does not execute backup
tools. `backup` may enter and leave an operational maintenance mode through a
lease interface but does not know HTTP or Vue details.

A host-side scheduler invokes pinned backup and host-sampling commands. The
application and worker never receive the Docker socket. Host container samples
are submitted to a separate internal listener with an HMAC-authenticated,
replay-protected envelope.

The public application listener continues to serve business and authenticated
admin APIs. A second internal listener serves Prometheus metrics and host
sample ingestion. It is bound only to the Docker private network in development
and to a loopback-only port when the production host sampler needs access.
Caddy never proxies the internal listener.

## 5. Data model

The next migration creates the following tables. UUID values are generated by
the application, timestamps are stored as `timestamptz`, and all state values
have database check constraints.

### 5.1 `system_settings`

This singleton row contains:

- `singleton_id boolean primary key default true check (singleton_id)`
- `version bigint not null check (version >= 1)`
- `site_name text not null`
- `site_announcement text not null default ''`
- `soft_delete_retention_days integer not null default 30`
- `audit_retention_days integer not null default 365`
- `operational_sample_retention_days integer not null default 7`
- `backup_hour integer not null default 3`
- `backup_minute integer not null default 0`
- `backup_timezone text not null default 'Asia/Shanghai'`
- warning and critical thresholds defined in section 9
- `updated_by uuid not null references users(id)`
- `updated_at timestamptz not null`

The retention ranges are 30–365 days for soft-deleted data, 365–2555 days for
audit records, and 1–30 days for operational samples. Audit retention is a
minimum; Phase 5 does not automatically purge the existing immutable audit
table. Backup hour is 0–23 and minute is 0–59. The business timezone remains
`Asia/Shanghai` in Phase 5; the field is stored so the contract is explicit
and future migrations do not need to infer it.

Updates require the current version and increment it exactly once. A stale
version maps to `settings_conflict`. Every successful update and rejected
high-risk value is audited without recording prior or new secrets.

### 5.2 `operational_modes`

The singleton operational row contains:

- `mode`: `normal | draining | backup | release`
- `owner_id uuid`
- `lease_token_hash bytea`
- `lease_expires_at timestamptz`
- `entered_at timestamptz`
- `updated_at timestamptz`
- `version bigint`

Only one lease owner may hold a non-normal mode. Lease renewal compares both
the owner and token hash. An expired lease is recoverable through a
compare-and-swap takeover that is audited. Returning to `normal` requires the
current token; a stale owner cannot clear a newer mode.

When mode is not `normal`, public unsafe HTTP methods return `503` with
`maintenance_mode`; authentication logout remains available. Background
claimers stop claiming new AI, processing, notification, and cleanup work.
Existing jobs finish under their current leases. The backup runner waits until
the durable active-job counts are zero and fails safely if the configured
ten-minute drain deadline is exceeded.

### 5.3 `backup_runs`

Each requested backup has:

- `id uuid primary key`
- `idempotency_key text not null`
- `trigger`: `scheduled | manual | pre_release`
- `state`: `queued | draining | snapshotting | encrypting | verifying |
  syncing | succeeded | degraded | failed`
- `requested_by uuid null references users(id)`
- `requested_at`, `started_at`, and `finished_at`
- `database_migration_version bigint`
- `encryption_key_id text`
- `local_snapshot_id text`
- `remote_snapshot_id text`
- `manifest_sha256 bytea`
- `logical_bytes bigint`
- `stored_bytes bigint`
- `local_expires_at timestamptz`
- `remote_expires_at timestamptz`
- `error_category text`
- `error_trace_id text`

`(trigger, idempotency_key)` is unique. A run may be `succeeded` only when the
local recovery point and integrity verification succeed. If the local point
succeeds but optional remote replication fails, the state is `degraded`. A run
with no verified local recovery point is `failed`.

Raw command output, repository credentials, object keys, student names, and
file names are not stored in this table.

### 5.4 `backup_artifacts`

Artifacts record the recovery point's logical components:

- `backup_run_id`
- `kind`: `database_dump | object_snapshot | manifest | recovery_report`
- `repository`: `local | remote`
- opaque `snapshot_id`
- `sha256`
- `size_bytes`
- `verified_at`
- `expires_at`

The primary key is `(backup_run_id, kind, repository)`. Repository paths are
not returned to the browser. The admin DTO exposes component state, size,
expiry, and verification time.

### 5.5 `restore_verifications`

Each disposable exercise records:

- `id uuid primary key`
- `backup_run_id`
- `state`: `queued | restoring | checking | succeeded | failed`
- `started_at` and `finished_at`
- `restored_migration_version`
- `database_row_counts jsonb`
- `checked_object_count bigint`
- `missing_object_count bigint`
- `unexpected_object_count bigint`
- `session_revocation_verified boolean`
- `rto_seconds bigint`
- `report_sha256 bytea`
- `error_category` and `error_trace_id`

`database_row_counts` contains only table names from a fixed allowlist and
integer counts. It never contains row values. A successful verification
requires zero missing referenced objects, no authorization regression, a
successful application readiness check, and proof that restored sessions were
revoked before the isolated application accepted traffic.

### 5.6 `operational_samples`

Samples contain:

- `source`: `app | postgres | redis | object_store | worker | host`
- `metric_name` from a fixed allowlist
- `scope` from a fixed service-name allowlist
- numeric `value`
- `unit`
- `observed_at`
- optional `window_started_at`

The primary access path is `(metric_name, scope, observed_at desc)`. Samples
are aggregate numbers only. User IDs, request IDs, URLs, file names, object
keys, prompts, and response content are rejected.

### 5.7 `operational_alerts` and `alert_deliveries`

An alert contains:

- `id uuid primary key`
- stable `dedupe_key`
- `category`
- `severity`: `warning | critical`
- `state`: `open | acknowledged | resolved`
- first/last observed timestamps
- acknowledgement actor and time
- resolution time
- current numeric value and threshold
- a safe summary and trace ID

Only one unresolved alert may exist for a dedupe key. Acknowledgement never
sets `resolved`; only a healthy evaluation can resolve the alert.

Delivery rows contain the alert, attempt number, destination kind, outcome,
HTTP status class, safe error category, started time, and finished time.
Webhook URLs, headers, and response bodies are never persisted.

## 6. Backup and recovery design

### 6.1 Recovery-point format

The backup implementation uses a pinned, deduplicating backup tool with
authenticated encryption and repository integrity checks. Repository
credentials are random owner-only secrets. An offline recovery bundle
containing the repository identifiers and recovery instructions is encrypted
to an Age X25519 recipient. The Age identity is not stored in the application,
database, container image, or Git repository.

This division preserves the approved Age-based recovery-key custody while
avoiding custom cryptography and full daily copies of unchanged AIStor data.
Every recovery point is tagged with the HappyLearn batch UUID and database
migration version.

### 6.2 Consistency protocol

The scheduled or manual runner:

1. Claims one queued run and one operational lease.
2. Enters `draining`, causing new writes and new worker claims to stop.
3. Waits up to ten minutes for durable active work to reach zero.
4. Enters `backup`.
5. Creates a PostgreSQL custom-format logical dump.
6. Stops AIStor cleanly through the host orchestrator.
7. Captures the PostgreSQL dump, AIStor data volume, and safe manifest in one
   encrypted recovery point.
8. Restarts AIStor and verifies authenticated readiness.
9. Runs repository integrity verification and verifies the manifest hash.
10. Copies the snapshot to the optional remote S3-compatible repository.
11. Applies retention.
12. Returns the operational mode to `normal` and records the terminal result.

Caddy serves a maintenance response during the consistent snapshot window.
The host orchestrator uses the exact production project name and Compose file
set. It never mounts the Docker socket into the app, worker, or backup
container.

If draining, dumping, stopping, snapshotting, restarting, or verification
fails, the runner records the exact safe stage, restarts any service it
stopped, and either returns to `normal` or leaves an explicit `release`
maintenance state when automatic recovery is not safe. No failure path silently
leaves a stale backup lease.

### 6.3 Retention

- Local repository: retain the newest seven successful daily recovery points.
- Remote repository: retain thirty successful daily and twelve successful
  monthly recovery points.
- Pre-release recovery points are protected from pruning for thirty days.
- A degraded run with a valid local point participates in local retention.
- Failed and abandoned temporary files are removed after 24 hours only when
  they are outside every committed snapshot.
- Prune executes only after a successful integrity check and never deletes the
  last successful recovery point.

### 6.4 Remote repository

Remote replication is disabled unless all S3 repository settings and secret
files are present. The endpoint must be HTTPS in production. TLS verification
cannot be disabled. Credentials are supplied as secret files and never through
command arguments.

Remote replication has bounded timeouts, resumable repository semantics, and
no automatic fallback to an unencrypted object copy. A remote outage creates
or updates a deduplicated `backup_remote_sync` alert.

### 6.5 Restore verification

The restore harness creates a unique disposable Compose project with empty
volumes and no public ports. It:

1. Selects a verified successful or degraded local recovery point.
2. Verifies repository integrity before restore.
3. Restores the PostgreSQL dump and AIStor data into empty volumes.
4. Revokes all restored sessions and rotates the isolated internal signing
   epoch before starting the application.
5. Starts the restored stack and verifies migrations and readiness.
6. Checks allowlisted row counts.
7. Enumerates every live database file reference and verifies the corresponding
   object and expected size.
8. Samples teacher and two-student authorization paths, including uniform 404
   behavior for cross-student identifiers.
9. Records duration and a sanitized report hash.
10. Removes the disposable containers, networks, and volumes.

Quarterly and post-migration scheduling is enforced by the operations runner.
The Phase 5 gate executes the exercise immediately, regardless of calendar.

## 7. Health, metrics, and host sampling

### 7.1 Application collectors

The application collects bounded queries for:

- application live and ready state;
- PostgreSQL connectivity, pool usage, transaction failure count, and current
  migration version;
- Redis ping latency and limiter availability;
- AIStor authenticated readiness, capacity, and object-operation failures;
- AI success/error rate, first-byte latency, total latency, token usage, and
  micro-USD cost;
- queued and failed file-processing jobs;
- queued, streaming, and expired AI runs;
- queued and failed outbox work;
- login failures, authorization denials, and denied file accesses;
- recent immutable audit activity grouped by safe action category;
- last local backup, last remote backup, and last restore verification.

Collectors use strict query timeouts. A failed collector returns an explicit
unknown or unavailable state and cannot mark a dependency healthy from stale
data.

### 7.2 Host sampler

A host systemd timer runs every minute. The sampler reads:

- production Compose service state and health;
- CPU percentage;
- memory usage and configured limit;
- restart count;
- root filesystem and backup filesystem capacity.

It signs a canonical JSON payload with HMAC-SHA256. The internal ingestion
endpoint requires a timestamp within 90 seconds and a nonce that has not been
used before. Service names and metric names are allowlisted; malformed or
unexpected labels are rejected and audited. The sampler does not submit
environment variables, mount paths, command lines, image registry credentials,
or raw logs.

### 7.3 Prometheus endpoint

The internal listener exposes `/internal/metrics`. It requires a dedicated
bearer token loaded from an owner-only secret file. The response contains only
bounded, aggregate metrics with fixed labels such as service, state, category,
and model alias. It must not contain user ID, student name, IP address, object
key, URL, prompt, lesson title, file name, request ID, or trace ID.

The public Caddy configuration returns 404 for `/internal/*` and never proxies
that prefix.

## 8. Teacher APIs and UI

### 8.1 API roots

All routes require an authenticated admin role, origin protection, CSRF for
mutations, `Cache-Control: no-store`, and request IDs.

- `GET /api/v1/admin/operations/dashboard`
- `GET /api/v1/admin/operations/settings`
- `PUT /api/v1/admin/operations/settings`
- `GET /api/v1/admin/operations/alerts`
- `POST /api/v1/admin/operations/alerts/{id}/acknowledge`
- `GET /api/v1/admin/operations/backups`
- `POST /api/v1/admin/operations/backups`
- `GET /api/v1/admin/operations/backups/{id}`
- `GET /api/v1/admin/operations/audit`
- `POST /api/v1/admin/operations/webhook-test`

Manual backup creation requires an `Idempotency-Key`. It creates a queued run;
the web request never invokes Docker or waits for the snapshot. Restore is not
an HTTP operation.

The webhook test sends a fixed synthetic payload without production metric
values or student information.

### 8.2 Stable errors

- `settings_conflict`
- `settings_invalid`
- `maintenance_mode`
- `backup_already_queued`
- `backup_unavailable`
- `alert_not_found`
- `alert_already_resolved`
- `webhook_not_configured`
- `webhook_delivery_failed`

Detailed causes remain in sanitized server logs and are correlated by the
returned trace ID.

### 8.3 Dashboard

`/admin` becomes the combined teaching and operational dashboard. It shows:

- active/disabled student counts;
- waiting teacher questions and oldest wait age;
- current AI request success rate and daily cost;
- storage use and configured warning threshold;
- unresolved warning and critical alerts;
- service health and dependency latency;
- processing and AI queue state;
- last local and remote backup;
- last restore verification and measured RTO.
- the ten most recent safe audit/activity summaries.

The default view refreshes every 60 seconds while visible. It stops polling when
the page is hidden and resumes with one immediate refresh. Stale data is labeled
with its observation time.

### 8.4 Operations pages

- `/admin/settings` edits the approved non-secret settings in grouped sections.
- `/admin/alerts` provides stable pagination, open/resolved filters, detail,
  acknowledgement, and the alert timeline.
- `/admin/backups` shows batch state, local and remote results, component sizes,
  retention expiry, and restore-verification history.
- `/admin/audit` provides stable keyset pagination and filters for safe action
  category, actor, target type, outcome, and time range. It never returns
  secret-bearing audit metadata.

Infrastructure secrets are represented only as configured/not configured and
last-validated timestamps.

Desktop uses summary cards plus health and backup panels. Mobile orders content
as alerts, backup, service health, queues, and summary statistics. Tables become
labeled cards. Color is never the sole status indicator. Existing keyboard,
screen-reader, focus, reduced-motion, and responsive contracts remain in force.

## 9. Alert rules

Defaults are stored in `system_settings`:

- disk warning at 75%, critical at 90%;
- backup filesystem warning at 75%, critical at 90%;
- no verified local backup for 25 hours is warning, 30 hours is critical;
- remote backup failure is warning when remote replication is configured;
- AI error rate warning at 10% and critical at 25% over a 15-minute window with
  at least 20 terminal runs;
- processing queue warning at 20 and critical at 100;
- processing failures warning at 5 in 15 minutes and critical at 20;
- login failures warning at 20 in 15 minutes and critical at 100;
- authorization denials warning at 50 in 15 minutes and critical at 200.

An alert opens after two consecutive failing evaluations one minute apart. It
resolves after three consecutive healthy evaluations. A critical threshold
upgrades an existing warning in place. Changes to threshold settings affect
future evaluations and do not rewrite alert history.

## 10. Webhook delivery

The webhook URL and authorization material come only from owner-only production
configuration. Production requires HTTPS. The transport reuses the Phase 4
safe outbound principles: DNS resolution classification, per-dial address
pinning, redirect rejection, request/response size limits, and bounded
timeouts. Private, loopback, link-local, metadata, multicast, documentation,
and otherwise non-public destinations are denied.

The JSON payload includes schema version, alert ID, category, severity, state,
safe summary, first/last observed time, current value, threshold, and dashboard
path. It excludes student information, IP addresses, object identifiers, URLs,
request bodies, prompts, and secrets.

Delivery retries at 1 minute, 5 minutes, and 30 minutes. Resolution notifications
use their own idempotency key. A failed webhook never blocks alert persistence
or resolution.

## 11. Logging and retention hardening

- Application and worker logs use structured JSON in production.
- Secret-like keys are rejected or redacted centrally.
- HTTP logs omit query strings and cookies.
- Container logs rotate at 10 MiB with five files.
- Audit records retain at least 365 days. Phase 5 does not weaken the existing
  immutable audit table with an application-level delete path.
- Operational samples retain seven days by default.
- Alert and backup metadata retain 365 days.
- Cleanup uses bounded batches, immutable audit entries, and the same safe
  lease patterns as existing maintenance work.

Passwords, full API keys, session cookies, CSRF tokens, backup repository
credentials, webhook URLs, signed URLs, student file bodies, AI attachments,
and full provider request/response bodies are forbidden in logs and metrics.

## 12. Failure handling

- Every external action has a timeout, idempotency boundary, durable state, and
  bounded retry policy.
- Runner leases are renewable and stale owners cannot commit terminal state.
- Local success plus remote failure is `degraded`, never `succeeded`.
- Repository integrity failure marks the run failed and prevents retention
  pruning.
- Temporary plaintext dumps exist only in an owner-only, capacity-bounded work
  directory and are removed on every terminal path. The gate searches for
  leaked dump signatures after injected failures.
- Unknown collector data remains unknown and opens a dependency-unavailable
  alert after the normal two-evaluation threshold.
- Teacher acknowledgement cannot suppress ongoing critical evaluation.

## 13. Testing strategy

### 13.1 Backend

- Migration up/down and constraint tests.
- Settings validation, optimistic conflict, transaction, and audit tests.
- Audit read allowlist, stable pagination, filter, role, and metadata-redaction
  tests.
- Operational lease acquisition, renewal, expiry, takeover, and stale-owner
  rejection.
- Backup state transitions, idempotency, degraded remote result, retention, and
  cleanup.
- Alert hysteresis, deduplication, acknowledgement, upgrade, and resolution.
- Webhook SSRF, DNS rebinding, redirect, timeout, payload, and retry tests.
- Metrics label allowlist and secret-leak regression tests.
- Host sample HMAC, timestamp, nonce replay, and label rejection tests.

### 13.2 Frontend

- Dashboard loading, healthy, degraded, stale, empty, and error states.
- Responsive ordering and mobile card conversion.
- Settings validation, dirty-state protection, conflict recovery, and focus.
- Alert filtering, acknowledgement, live resolution, and pagination.
- Backup history and local/remote distinction.
- Recent-activity and audit filtering, pagination, and redaction.
- Keyboard, accessible name, status text, reduced motion, and polling lifecycle.

### 13.3 Integration and recovery

- Licensed AIStor versioning and clean shutdown snapshot.
- Real PostgreSQL custom dump.
- Encrypted local recovery point and integrity check.
- Optional S3-compatible repository success, outage, partial transfer, and
  retry.
- Wrong repository secret and tampered repository detection.
- Retention with protected pre-release points and last-good protection.
- Full disposable empty-environment restore and object-reference verification.
- Session revocation after restore.
- Failure injection at drain, dump, AIStor stop, snapshot, restart, verify,
  remote copy, and prune stages.

### 13.4 End to end and security

- Teacher views dashboard and recent audit activity, changes settings, queues a
  backup, acknowledges an alert, and inspects restore evidence.
- Student and unauthenticated requests cannot access operations APIs or metrics.
- Caddy/public route rejects `/internal/*`.
- Logs, diagnostics, browser artifacts, repository metadata, and Prometheus
  output pass secret and student-data scans.
- Desktop Chromium and the established mobile viewport pass.
- The steady stack and backup maintenance peak remain within 2 CPU and 4 GB,
  with worker/backup mutual exclusion proven by live capture.

## 14. Completion gate

Phase 5 is complete only when:

1. Every implementation plan task has RED/GREEN evidence.
2. Backend ordinary, serialized integration, race, vet, and reachable-code
   vulnerability checks pass.
3. Frontend test, typecheck, lint, build, desktop, and mobile gates pass.
4. All shell, Compose, workflow, and artifact-sanitization contracts pass.
5. A licensed real PostgreSQL and AIStor backup succeeds.
6. The backup restores into an empty disposable environment and passes
   reference, authorization, readiness, and session-revocation checks.
7. Optional remote S3 success and failure behavior is proven with the local
   compatible fixture.
8. Healthy scheduled operation proves an RPO no greater than 24 hours, and the
   empty-environment exercise proves an RTO no greater than 4 hours.
9. Live resource capture proves the 2 CPU and 4 GB limit.
10. Complete-diff review has no open Critical or Important finding.
11. The operations runbook is complete and the repository is clean.
