# HappyLearn Phase 3 老师答疑与站内通知设计规格

日期：2026-07-22  
状态：用户已批准

## 1. 目标与范围

Phase 3 在已验收的认证、学生管理、教学发布和安全文件能力之上，交付私密老师答疑、不可变消息时间线、答疑附件、站内通知和课程发布通知消费。目标环境继续是 Ubuntu 24.04、2 核 CPU、4 GB 内存、Docker，以及 1 名老师和最多 50 名学生。

每道问题建立一个独立答疑线程。学生只能读取自己的线程、消息、附件和通知；老师可以处理所有学生线程、回复、改变状态，并写入仅老师可见的内部备注。所有消息只追加，不允许修改或删除。

本阶段不包含：

- AI 答疑、模型配置、流式生成、Token 或费用记账；
- 邮件、短信、微信或浏览器推送；
- WebSocket、SSE 或跨设备实时协作编辑；
- 富文本消息、公开问答、学生互相交流；
- 消息编辑、撤回、静默覆盖或物理删除；
- 作业、测验、批改、成绩和排名。

## 2. 已确认的产品决定

- 通知采用 15 秒短轮询；页面重新获得焦点时立即刷新。
- 每道新问题创建独立线程，不建立每名学生一个长期私聊线程。
- 学生问题和双方回复使用纯文本加安全换行，不引入消息 Markdown 或 HTML。
- 状态为 `pending`、`in_progress`、`waiting_student`、`completed`。
- 学生创建问题后状态为 `pending`；学生追问后回到 `pending`；老师回复后默认进入 `waiting_student`。
- 老师可以显式切换到 `in_progress` 或 `completed`，并可重新打开已完成线程。
- 内部备注与消息分表存储，只对老师可见；学生响应不泄露备注是否存在。
- 附件复用 Phase 2 的私有对象存储、分片上传、真实类型检测、恶意文件扫描、预览和受控下载能力。
- 课程发布 outbox 在本阶段开始生成站内通知。
- Phase 4 可以复用线程、消息、附件和通知边界，但 AI 运行、流式输出和用量仍由独立模块负责。

## 3. 架构与模块边界

继续采用模块化事务单体，不引入独立消息服务。

### 3.1 `qanda`

负责答疑线程、消息、状态机、内部备注、幂等提交、老师队列和学生私有查询。该模块依赖窄化后的文件可绑定/可访问接口、通知写入接口和审计写入接口，不读取 MinIO 对象键。

### 3.2 `notifications`

负责通知记录、未读计数、游标列表、单条已读、全部已读和轮询响应。通知只保存安全摘要和业务链接，不复制完整问题正文、回复正文、附件名称或对象键。

### 3.3 `events`

负责以租约领取 `outbox_events`、有限退避重试和幂等发布。Phase 3 消费 `lesson.published` 事件并按照发布版本受众创建课程通知。答疑写操作在同一数据库事务中直接写入通知，因此用户可见状态和通知不会半成功；outbox 只承担跨阶段已有发布事件和适合异步扇出的工作。

### 3.4 `files`

扩展现有上传用途和访问授权，不复制上传实现。文件模块验证上传者、业务用途、处理状态、类型、数量和总大小；答疑模块只接收已通过验证的文件版本标识。课程附件与答疑附件使用不同的业务授权查询。

## 4. 数据模型

所有业务标识使用不可预测 UUID，时间统一存储为带时区时间。状态、角色、唯一性、外键和不可变性由 PostgreSQL 约束和触发器共同保证。

### 4.1 `qa_threads`

- `id`：线程 UUID；
- `student_id`：线程所有学生；
- `title`：规范化标题，1–160 个 Unicode 字符；
- `status`：四种固定状态；
- `version`：状态和最新活动的乐观并发版本；
- `last_message_at`：稳定排序字段；
- `created_at`、`updated_at`、`completed_at`。

线程不能在学生之间转移。列表稳定排序为 `last_message_at DESC, id DESC`，游标同时携带两项。

### 4.2 `qa_messages`

- `id`、`thread_id`、`sender_user_id`；
- `sender_role`：`admin` 或 `student` 的发送时快照；
- `body_text`：规范化纯文本，1–20,000 个 Unicode 字符；
- `idempotency_key`：调用者作用域内唯一；
- `created_at`。

数据库拒绝更新和删除消息。发送者必须是线程所属学生或当前老师；服务层和数据库事务边界都执行验证。

### 4.3 `qa_message_files`

- `message_id`、`file_version_id`、`sort_position`；
- `display_name`：绑定时规范化的显示名称快照；
- 复合主键和唯一排序约束。

绑定写入后不可更新或删除。一个文件版本不能借由答疑绑定扩大到其他线程或其他学生。

### 4.4 `teacher_notes`

- `id`、`thread_id`、`author_user_id`、`body_text`、`created_at`。

备注只追加，不支持编辑或删除。学生侧查询、DTO、错误和计数均不包含备注字段。

### 4.5 `notifications`

- `id`、`recipient_user_id`；
- `kind`：`qa_created`、`qa_replied`、`qa_followed_up`、`qa_status_changed`、`lesson_published`；
- `title`、`summary`、`target_type`、`target_id`、`target_path`；
- `dedupe_key`：接收者作用域内唯一；
- `read_at`、`created_at`。

未读索引覆盖 `recipient_user_id, created_at DESC, id DESC WHERE read_at IS NULL`。标记已读必须限定当前接收者。

### 4.6 Outbox 扩展

在现有 `outbox_events` 上增加领取租约、尝试次数、下次重试时间、最后稳定错误类别和唯一幂等键。消费者只有在目标通知全部按 `dedupe_key` 落库后才标记事件完成。崩溃重试不得生成重复通知。

## 5. 状态机与权限

允许的状态转换：

- 创建：无 → `pending`；
- 老师领取：`pending` → `in_progress`；
- 老师回复：`pending`/`in_progress`/`waiting_student` → `waiting_student`；
- 学生追问：`waiting_student`/`in_progress`/`completed` → `pending`；
- 老师完成：`pending`/`in_progress`/`waiting_student` → `completed`；
- 老师重新打开：`completed` → `in_progress`。

学生不能直接改变状态。对已完成线程追问等价于追加消息并重新打开为 `pending`。所有状态变更携带期望 `version`；不匹配返回 `409 thread_conflict`，不进行静默覆盖。

学生 SQL 查询始终包含 `student_id = 当前用户` 和启用账号条件。不存在、未授权、属于其他学生或已不可访问的线程统一返回 `404 not_found`。老师接口同时要求管理员角色。禁用学生后，其现有会话被撤销，后续 SQL 查询也拒绝其线程、通知和附件。

## 6. 附件策略

### 6.1 限制

- 单张 JPEG、PNG、WebP 或非动画 GIF ≤20 MB；
- 每条消息最多 10 张图片；
- 单个 PDF ≤50 MB；
- 单个 DOCX、XLSX 或 PPTX ≤30 MB；
- 每条消息所有附件合计 ≤100 MB；
- 允许 TXT 和 Markdown，单个 ≤10 MB；
- 拒绝压缩包、可执行文件、脚本、宏 Office、SVG、HTML、声明类型与真实类型不一致的文件。

### 6.2 上传和绑定

上传会话包含 `purpose=qa_attachment` 和所有者。客户端先完成上传并等待 `ready`，再将文件版本 UUID 放入创建问题或回复请求。服务端事务内重新验证：所有权、用途、状态、数量、单项限制、合计大小和未被不兼容业务占用。未就绪返回 `409 attachment_not_ready`；不合法类型返回稳定的文件错误码。

### 6.3 访问

答疑附件通过同源受控端点访问。授权查询必须证明当前用户是线程学生或管理员，并且文件版本绑定到该线程的不可变消息。响应继续设置 `nosniff`、私有禁止缓存和规范化 `Content-Disposition`。每次允许、拒绝和失败写入访问日志；越权不返回文件名、对象键或线程存在性。

## 7. HTTP API

所有端点位于 `/api/v1`，复用现有会话认证、Origin、CSRF、请求 ID、稳定错误封装和客户端 IP 规范化。

### 7.1 学生答疑

- `GET /student/questions`：按状态和稳定游标列出本人线程；
- `POST /student/questions`：以 `Idempotency-Key` 创建线程和首条消息；
- `GET /student/questions/{id}`：读取本人线程、消息和安全附件视图；
- `POST /student/questions/{id}/messages`：以 `Idempotency-Key` 追问；
- `GET /student/questions/{id}/messages`：按正序游标读取历史消息。

### 7.2 老师答疑

- `GET /admin/questions`：按状态、学生、日期和稳定游标筛选；
- `GET /admin/questions/{id}`：读取完整消息时间线和内部备注；
- `POST /admin/questions/{id}/messages`：以 `Idempotency-Key` 回复；
- `POST /admin/questions/{id}/status`：携带期望版本改变状态；
- `POST /admin/questions/{id}/notes`：追加内部备注。

### 7.3 通知

- `GET /notifications?cursor=&limit=`：当前用户的通知；
- `GET /notifications/unread-count`：返回当前用户未读数；
- `POST /notifications/{id}/read`：幂等标记单条已读；
- `POST /notifications/read-all`：幂等标记当前时点以前的全部通知已读。

### 7.4 答疑上传和文件访问

- `POST /student/question-uploads` 和对应状态、分片、完成、取消子路由；
- `POST /admin/question-uploads` 和对应子路由；
- `GET /question-files/{version}/preview`；
- `GET /question-files/{version}/download`。

上传 HTTP 层复用共同处理器，只通过策略对象区分角色、用途和限制。

## 8. 事务、幂等和通知数据流

### 8.1 创建问题

1. 学生上传附件并等待处理完成。
2. 服务端认证、校验 `Idempotency-Key`、正文和附件。
3. 一个事务创建线程、首条消息、附件绑定、老师通知和审计记录。
4. 重复键返回第一次创建的线程，不重复消息、通知或审计业务事件。

### 8.2 老师回复

1. 服务端锁定线程并校验期望版本和附件。
2. 一个事务追加老师消息、更新状态和活动时间、创建学生通知并写入审计。
3. 提交后学生下一次轮询或打开页面即可读取。

### 8.3 学生追问

一个事务追加消息，将线程恢复为 `pending`，递增版本，创建老师通知并写入审计。已完成线程允许通过追问重新打开。

### 8.4 课程发布通知

事件消费者按租约领取 `lesson.published`，读取不可变发布版本的受众快照，为仍启用且有权访问的学生逐一插入带确定性 `dedupe_key` 的通知。课程撤回不会删除历史通知，但学生点击后仍由当前课程授权决定是否可读。

## 9. 前端体验

### 9.1 学生端

- `/student/questions`：状态筛选、最近活动排序、空/加载/错误状态；
- `/student/questions/new`：标题、正文、附件上传和明确提交状态；
- `/student/questions/:id`：单栏不可变时间线、状态、附件预览/下载和追问；
- 手机端保持单栏，输入区不遮挡最近消息。

### 9.2 老师端

- `/admin/questions`：桌面使用筛选列表加详情双栏，手机降级为列表到详情导航；
- 支持状态、学生和日期筛选；
- 详情显示学生消息、老师回复、附件、状态操作和独立内部备注区；
- 内部备注使用明显的“仅老师可见”样式，不混入学生可见时间线。

### 9.3 通知中心

- `/notifications`：当前用户通知列表、单条已读和全部已读；
- 控制台顶部显示真实未读数；
- 登录后启动 15 秒轮询，页面隐藏时暂停，重新可见或窗口聚焦时立即刷新；
- 注销、组件卸载或账号切换时必须清理定时器和在途请求；
- 通知链接只跳转到当前角色可访问的站内路径，服务端仍重新鉴权。

## 10. 错误处理、隐私与审计

稳定业务错误至少包括：

- `thread_conflict`；
- `attachment_not_ready`、`attachment_limit_exceeded`；
- `invalid_status_transition`；
- `idempotency_key_required`、`idempotency_conflict`；
- `not_found`、`forbidden`、`rate_limited`。

对外错误不包含数据库结构、对象键、其他学生 UUID 或内部状态。服务端日志和审计不得保存问题正文、回复正文、内部备注正文、附件文件名、会话令牌或对象键。审计只记录动作、参与者、线程 UUID、安全计数/状态摘要、请求 ID 和客户端 IP。

敏感写操作包括创建问题、追问、回复、状态改变、内部备注、通知批量已读和附件访问。答疑消息与内部备注使用数据库触发器拒绝更新和删除。

## 11. 资源与运行约束

- 15 秒轮询只查询当前用户的索引化未读计数，响应禁止缓存；
- 单页最大 50 条线程、100 条消息或 100 条通知；
- 文件上传和访问保持流式，不缓冲完整文件；
- 文件处理并发继续固定为 1；
- outbox 消费批次有硬上限，租约过期可被安全接管；
- PostgreSQL 保存业务真相，Redis 只用于限频等短期协调；Redis 故障不能丢失线程或通知；
- 不新增公网端口，MinIO、PostgreSQL 和 Redis 继续保持私有。

## 12. 测试策略

### 12.1 单元测试

- 全部合法和非法状态转换；
- 学生/老师权限和统一非枚举错误；
- 标题、正文、附件数量与大小限制；
- 幂等创建、追问和回复；
- 通知去重、未读计数和已读操作；
- 短轮询启动、暂停、恢复和清理。

### 12.2 PostgreSQL 集成测试

- 外键、唯一约束、不可变消息/备注/附件绑定；
- 创建、回复和追问事务在审计或通知失败时完全回滚；
- 两个学生之间在线程、消息、通知和文件查询层隔离；
- 状态乐观并发；
- outbox 租约、崩溃重试和通知幂等；
- 课程全体/指定学生受众通知。

### 12.3 HTTP 和前端测试

- 角色限制、CSRF、Origin、严格 JSON、游标和请求 ID；
- 学生创建问题、筛选、时间线和追问；
- 老师队列、回复、完成、重新打开和内部备注；
- 学生渲染树与网络响应均不包含内部备注；
- 附件处理状态、访问允许和跨学生拒绝；
- 通知列表、链接、未读角标和已读操作；
- 桌面双栏和手机单栏的键盘可访问性。

### 12.4 端到端验收

1. 学生 A 创建带附件的问题，老师收到通知并可读取。
2. 学生 B 无法通过列表、UUID、附件 UUID 或通知确认该问题存在。
3. 老师领取、回复并完成问题；学生 A 收到通知并继续追问，线程回到 `pending`。
4. 老师添加内部备注，任何学生响应和页面均不可见。
5. 课程发布为全体或指定学生生成正确且不重复的通知。
6. 禁用学生后，其线程、通知和答疑附件立即不可访问。
7. 刷新、重复点击和网络重试不产生重复消息或通知。
8. 桌面和手机浏览器完成列表、详情、回复和通知流程。

完整门禁包括 Go 单元/集成/竞态、`go vet`、`govulncheck`、前端单元/类型/lint/构建/依赖审计、Docker Compose 与镜像检查，以及 Playwright 全链路验收。

## 13. Phase 3 验收标准

1. 学生能创建独立私密问题、上传安全附件、查看不可变时间线并继续追问。
2. 老师能筛选全部问题、回复、改变状态、完成和重新打开，并添加仅老师可见备注。
3. 任意学生都无法确认其他学生的线程、消息、附件、通知或内部备注存在。
4. 创建、回复、追问、状态和通知在事务失败时不留下半成功状态。
5. 重复请求和 outbox 重试不会重复创建消息、线程或通知。
6. 附件类型、大小、数量、扫描和访问权限均由后端强制执行。
7. 课程发布、老师回复、学生追问和状态变化产生正确的站内通知。
8. 通知中心支持列表、未读数、单条已读、全部已读和安全业务跳转。
9. 15 秒轮询在页面隐藏、注销、卸载和账号切换时正确暂停或清理。
10. 禁用学生后，下一次答疑、通知和附件请求立即失效。
11. 所有消息、备注和绑定保持不可变，日志与审计不泄露正文或文件秘密。
12. 完整测试、安全、资源和桌面/手机验收全部通过，无未处理的 Critical 或 Important 问题。

## 14. 实施分解

Phase 3 按以下顺序实施，每个交付门都保持应用可运行：

1. 答疑 schema、状态机、学生线程和 SQL 隔离；
2. 老师队列、回复、状态、内部备注和审计；
3. 答疑上传、不可变附件绑定与受控访问；
4. 通知存储、轮询 API 和 outbox 消费；
5. 学生/老师 Vue 界面与通知中心；
6. 全链路 E2E、容器加固、运行手册和 Phase 3 完整门禁。
