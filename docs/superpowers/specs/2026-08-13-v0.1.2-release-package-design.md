# v0.1.2 Release Package Design

## Goal

Publish annotated tag `v0.1.2` from the verified `master` commit and create an immutable GitHub Release containing `VAYZRA-v0.1.2.tar.gz` plus `SHA256SUMS`.

## Scope

- Preserve the existing stable SemVer, `master` ancestry, exact Verify-run, tag-object, and test/build gates.
- Package the tagged repository source with the top-level directory `VAYZRA-v0.1.2/`.
- Generate a SHA-256 manifest whose entry uses the portable relative filename `VAYZRA-v0.1.2.tar.gz`.
- Transfer the two generated files between jobs with a pinned GitHub artifact action.
- Create the Release as a draft, attach both files, and only then publish it so release immutability can protect the complete asset set.
- Keep Phase 6 production images, SBOMs, manifests, and registries outside this workflow.

## Release Flow

1. A pushed annotated tag matching `vMAJOR.MINOR.PATCH` starts `github-release`.
2. The validation job peels the event tag to the exact commit, verifies that it belongs to `master`, and requires the successful full `verify.yml` push run for that commit.
3. The validation job installs dependencies and runs the existing update-agent and web checks.
4. The validation job builds a deterministic source archive from the verified tag commit, validates its top-level prefix, writes `SHA256SUMS`, verifies the checksum, and uploads exactly those two files as a short-lived workflow artifact.
5. The publish job revalidates the remote tag, downloads the workflow artifact, verifies filenames, archive prefix, and checksum, creates a draft GitHub Release with generated notes, uploads both assets, then publishes the draft.
6. Post-publication verification must confirm the Release is non-draft, non-prerelease, points to `v0.1.2`, contains the two expected assets, and reports `immutable=true` for OTA eligibility.

## Failure Handling

- Any mismatch in tag syntax, peeled commit, branch ancestry, Verify result, archive layout, checksum, or asset set fails before publication.
- A failed validation job creates no Release.
- A failure while assembling or uploading the draft leaves no published Release; the draft can be inspected and removed before retrying.
- If the published Release does not report `immutable=true`, the release is not considered OTA-ready and the task must report the repository-setting blocker rather than claiming success.

## Testing

- Extend `scripts/github-ota_contract_test.sh` first so the current metadata-only workflow fails the new package contract.
- The contract must require pinned upload/download actions, portable archive/checksum generation, draft creation with both assets, and explicit publication after upload.
- Run the focused GitHub OTA contract, YAML parsing/Compose contracts reached by the normal verification target, shell syntax checks, and `git diff --check` before committing.
- Push the workflow change to `master`, wait for the full Verify workflow to succeed, then create and push the annotated tag.
- Monitor `github-release` to completion and inspect the final Release and downloadable assets.

## Non-Goals

- Building or publishing application, worker, migration, backup, or update-agent container images.
- Publishing npm packages or GitHub Packages registry entries.
- Treating the GitHub Release as the approved Phase 6 production release pipeline.
