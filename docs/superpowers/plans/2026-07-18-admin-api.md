# HappyLearn Teacher Administration API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Expose secure browser authentication, resilient login throttling, one-teacher bootstrap, audited student lifecycle APIs, and strict admin authorization on top of the foundation data layer.

**Architecture:** HTTP handlers depend on the authentication service and stable JSON helpers created in `2026-07-18-foundation-auth.md`. Same-origin and double-submit CSRF middleware protect mutations; Redis coordinates throttling while a local fallback keeps protection available; student writes and audit rows share PostgreSQL transactions.

**Tech Stack:** Go 1.26.5, chi, pgx v5, Redis 8.8, PostgreSQL 18.4, standard `net/http` tests, Testcontainers or local Compose services.

## Global Constraints

- Execute `docs/superpowers/plans/2026-07-18-foundation-auth.md` first.
- Exactly one teacher administrator is allowed; public registration does not exist.
- Students must change temporary passwords on first login and cannot access any admin endpoint.
- Session cookies are opaque, `HttpOnly`, `Secure` in production, `SameSite=Lax`, idle for 7 days maximum and absolute for 30 days maximum.
- State-changing requests require exact same-origin validation and matching nonempty CSRF cookie/header values.
- Passwords, hashes, session tokens, CSRF tokens, and request bodies never enter audit metadata or logs.
- Redis failure must not disable all logins and must not remove bounded brute-force protection.
- Use TDD, parameterized SQL, explicit errors, ownership/role checks, and frequent commits.

- [ ] **Step 3: Implement atomic, privacy-preserving counters**

HMAC the normalized username and canonical IP with an application-specific secret before building Redis keys. Use one Lua script to increment and set expiry atomically. Five account failures or twenty IP failures in 15 minutes cause a 15-minute block; three account failures set `ChallengeRequired=true`. Successful login clears the account failure key, not the shared IP key.

When a challenge is required, `GET /auth/challenge` returns a random challenge ID and a server-rendered distorted PNG containing five unambiguous uppercase characters. Store only an HMAC of the normalized answer in Redis for five minutes; verification is one-time and constant-time. The PNG response is 
o-store`, capped at 50 KiB, and generated without user input. Add tests for expiry, replay, wrong answer, and Redis-down behavior (temporarily reject challenged attempts rather than bypass the challenge).

- [ ] **Step 4: Implement and test Redis-down fallback**

When Redis is unavailable, allow an attempt only through an in-process token bucket of one attempt per account/IP per 10 seconds. Emit a sanitized metric and warning without usernames/IPs. Add a test using a closed Redis client proving the second immediate attempt is rejected locally; never fail completely open or lock out every user.

- [ ] **Step 5: Integrate with generic login errors**

Before password verification call `Allow`. On block return HTTP 429, error code `login_rate_limited`, a generic Chinese message, and rounded `Retry-After`; never disclose whether the account exists. When `ChallengeRequired`, reject missing/invalid challenge with code `login_challenge_required` and a fresh challenge URL before doing Argon2 work. Record each failure and clear after success.

## Completion Gate

- All auth mutations reject cross-origin and missing/mismatched CSRF requests.
- Wrong username and wrong password have the same status and JSON error shape.
- Redis outage still applies bounded local throttling without disabling all logins.
- A second administrator cannot be bootstrapped.
- Students receive 403 from every admin student endpoint.
- Disable/reset operations revoke sessions and write immutable, secret-free audit events.
- `go test -race ./...` passes before starting the console plan.
